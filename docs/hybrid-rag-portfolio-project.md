# Sourcerer — Portfolio Project Blueprint

> ผู้ช่วยตอบคำถามจากเอกสารของคุณ พร้อมอ้างอิงแหล่งที่มาเสมอ
> ชื่อ Sourcerer เล่นคำจาก *source* + *sorcerer* สื่อว่าทุกคำตอบยึดกับแหล่งที่มาที่อ้างอิงได้

**Sourcerer** คือผู้ช่วยตอบคำถามจากเอกสารภายในองค์กร ที่ใช้สถาปัตยกรรม **hybrid** (local LLM + API), **hybrid retrieval** (vector + keyword + reranker), มี **evaluation harness** และพร้อมขึ้น production — ออกแบบมาเพื่อโชว์ทักษะ LLM Engineer ครบทุกชั้น

---

## ทำไมโปรเจกต์นี้ถึงเหมาะกับ Portfolio

คนจ้างงานสาย LLM ไม่ได้ดูว่าคุณเรียก API เป็นไหม (ใครๆ ก็ทำได้) แต่ดูว่าคุณ "ทำของที่ใช้งานจริงได้และวัดผลได้" หรือเปล่า โปรเจกต์นี้จงใจใส่จุดที่แยกมือสมัครเล่นออกจากมืออาชีพไว้ 3 จุด:

1. **Hybrid retrieval ที่วัดผลได้** ไม่ใช่แค่ vector search เปล่าๆ
2. **Evaluation harness** มีตัวเลขพิสูจน์ว่าระบบดีจริง ไม่ใช่ "ดูเองแล้วน่าจะโอเค"
3. **Routing local vs API** โชว์ความเข้าใจเรื่องต้นทุน ความเป็นส่วนตัว และ trade-off จริงในองค์กร

## สถาปัตยกรรมเป้าหมาย

```
                    ┌─────────────────────────────────────┐
   เอกสาร ──────►   │  Ingestion: chunk + embed + index    │
 (PDF/MD/HTML)      └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
   คำถามผู้ใช้ ──►   │  Hybrid Retrieval                    │
                    │  vector (pgvector) + BM25 + reranker │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  Router: งานง่าย/อ่อนไหว → local      │
                    │          งานยาก → API (frontier)     │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  Generation + citations              │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  Eval harness + logging/observability│
                    └─────────────────────────────────────┘
```

### ตัวเลือกเทคโนโลยีแต่ละชั้น

| ชั้น | เลือกใช้ | เหตุผล |
|------|---------|--------|
| Local inference | **Ollama** (dev) → **vLLM** (prod) | เส้นทางมาตรฐานของ enterprise |
| โมเดล local | **Qwen 2.5 32B** หรือ **Llama 3.x** quantized (INT4) | ขนาด "local-grade" ที่คุ้มสุดในตอนนี้ |
| โมเดล API | Claude / GPT (ตัว frontier) | ไว้เทียบ baseline + รับงานยาก |
| Vector DB | **pgvector** (เริ่ม) หรือ **Qdrant/Weaviate** | pgvector ต่อยอด Postgres เดิมได้ คุมง่าย |
| Keyword | **BM25** (ผ่าน Postgres FTS หรือ OpenSearch) | ครึ่งหนึ่งของ hybrid retrieval |
| Reranker | **bge-reranker** หรือ Cohere Rerank API | ดันความแม่นของผลลัพธ์ขึ้นชัดเจน |
| Orchestration | **LlamaIndex** หรือเขียนเอง | เขียนเองรอบแรกเพื่อเข้าใจกลไก |
| Embedding | **bge-m3** หรือ OpenAI embeddings | เลือกที่รัน local ได้เพื่อความสอดคล้องกับธีม |
| Backend/API | **FastAPI** | มาตรฐาน Python สำหรับ serve |
| Frontend | Streamlit (เร็ว) หรือ Next.js (โชว์ฝีมือ) | แล้วแต่เวลา |

> เลือก dataset ที่ "ตอบยากด้วย ChatGPT ทั่วไป" เช่น เอกสาร internal นโยบายบริษัท, คู่มือเทคนิคเฉพาะทาง, หรือ corpus เปิดสักชุด (เช่น เอกสารกฎหมาย/การแพทย์ที่เปิดสาธารณะ) ยิ่งเฉพาะทางยิ่งโชว์คุณค่าของ RAG

## แบ่งเป็น 5 Phase

### Phase 1 — MVP RAG (สัปดาห์ 1)
เป้าหมาย: ทำให้ปลายทางทำงานทะลุก่อน แล้วค่อยปรับคุณภาพ

- ตั้ง Ollama + ดึงโมเดลมารัน local
- เขียน ingestion pipeline ง่ายๆ: โหลดเอกสาร → chunk → embed → เก็บลง pgvector
- เขียน retrieval แบบ vector search ล้วน → ส่ง context เข้าโมเดล → ตอบพร้อม citation
- ห่อด้วย FastAPI + UI ง่ายๆ

**ส่งมอบ:** ถามแล้วได้คำตอบที่อ้างอิงเอกสารได้ แม้ยังไม่เนียน

### Phase 2 — Hybrid Retrieval (สัปดาห์ 2)
เป้าหมาย: ยกคุณภาพการ retrieve ซึ่งเป็นหัวใจจริงของ RAG

- เพิ่ม BM25 keyword search ขนานกับ vector
- รวมผลสองทางด้วย reciprocal rank fusion (RRF)
- เพิ่ม reranker มา re-score ผลลัพธ์ก่อนส่งเข้าโมเดล
- ทดลอง chunking หลายแบบ (fixed-size vs semantic vs contextual)

**ส่งมอบ:** เทียบให้เห็นว่า hybrid + reranker ดีกว่า vector ล้วนอย่างไร (ต่อยอดใน Phase 3)

### Phase 3 — Evaluation Harness (สัปดาห์ 2–3) ⭐ จุดเด่นที่สุด
เป้าหมาย: พิสูจน์ด้วยตัวเลข นี่คือสิ่งที่ทำให้ portfolio คุณโดดกว่าคนอื่น 90%

- สร้าง eval set: คู่ (คำถาม, คำตอบที่ถูก, เอกสารที่ควร retrieve) สัก 50–100 ข้อ
- วัด **retrieval metrics**: recall@k, MRR, hit rate
- วัด **generation metrics**: faithfulness (ตอบตรงตาม context ไหม), answer relevancy — ใช้แนวทาง LLM-as-judge
- ทำตารางเทียบ config ต่างๆ (vector ล้วน vs hybrid vs hybrid+rerank) ให้เห็นตัวเลขชัด
- เครื่องมือช่วย: **RAGAS** หรือเขียน harness เอง

**ส่งมอบ:** ตารางผล + กราฟที่บอกว่า "config ไหนดีสุดเพราะอะไร"

### Phase 4 — Hybrid Routing (สัปดาห์ 3–4)
เป้าหมาย: โชว์ความเข้าใจเรื่องต้นทุน/ความเป็นส่วนตัว แบบที่องค์กรจริงสนใจ

- เขียน router: classify คำถามว่า "ง่าย/อ่อนไหว" → local, "ยาก/ต้องเหตุผลซับซ้อน" → API
- จับ metric: สัดส่วนงานที่ไป local, ต้นทุนต่อ query, latency แต่ละทาง
- คำนวณว่าประหยัดได้กี่ % เทียบกับยิง API ล้วน (เป้าอ้างอิงในอุตสาหกรรม ~40–70%)

**ส่งมอบ:** กราฟ cost/latency + เหตุผลการ route ที่อธิบายได้

### Phase 5 — Production Polish (สัปดาห์ 4)
เป้าหมาย: ทำให้ดูเหมือนของจริง ไม่ใช่ของเล่น

- ย้าย inference จาก Ollama → **vLLM** วัด throughput ที่เพิ่มขึ้น
- ใส่ observability: logging ทุก query, retrieval trace, token/cost tracking
- ใส่ guardrails: จัดการกรณีไม่มีคำตอบใน context (ตอบ "ไม่ทราบ" แทนการมั่ว), ตรวจ prompt injection เบื้องต้น
- Dockerize ทั้งระบบด้วย docker-compose
- เขียน README ให้ดี (สำคัญมาก — ดูด้านล่าง)

**ส่งมอบ:** repo ที่ `docker-compose up` แล้วรันได้ทันที

## Stretch Goals (ถ้ามีเวลาเหลือ)

- **Agentic RAG**: ให้โมเดลตัดสินใจเองว่าต้อง retrieve กี่รอบ, query อะไรเพิ่ม
- **Multi-hop questions**: คำถามที่ต้องรวมข้อมูลจากหลายเอกสาร
- **Air-gapped mode**: รันได้แบบตัดเน็ตทั้งหมด (จุดขายของ enterprise สาย compliance)
- **A/B eval อัตโนมัติ**: รัน eval ทุกครั้งที่เปลี่ยน config ผ่าน CI

## Phase 6 (ทางเลือกต่อยอด) — GraphRAG ⭐ จุดที่ทำให้ portfolio โดดเด่น

ถ้าทำ Phase 1–5 เสร็จแล้วอยากยกระดับให้ห่างจาก portfolio ทั่วไป นี่คือส่วนต่อยอดที่คุ้มค่าที่สุด และเป็นที่นิยมในอุตสาหกรรมมากกว่า KAG เต็มรูปแบบ

### GraphRAG คืออะไร และต่างจาก RAG ปกติยังไง

GraphRAG (ของ Microsoft) เกิดมาแก้จุดอ่อนเฉพาะอย่างหนึ่งของ vector RAG คือ RAG ปกติ **ตอบคำถามภาพรวมทั้ง corpus ไม่ได้** เพราะมันค้นด้วยความคล้ายของข้อความ คำถามอย่าง "ธีมหลัก 5 อันดับในข้อมูลทั้งหมดคืออะไร" จึงทำได้แย่ เนื่องจากไม่มีอะไรในคำถามชี้ไปยังข้อความที่ถูกต้อง GraphRAG แก้ด้วยการสร้างโครงสร้างกราฟที่บอก "ภาพรวม" ของชุดข้อมูลล่วงหน้า

กลไกทำงานเป็น 2 ขั้นใหญ่:

1. **Indexing** — ใช้ LLM สกัด entity และความสัมพันธ์ออกจากเอกสารมาสร้างเป็น knowledge graph จากนั้นจัดกลุ่ม node เป็น "community" แบบลำดับชั้น (Microsoft ใช้อัลกอริทึม Leiden) แล้วให้ LLM เขียนสรุปของแต่ละ community ไว้ล่วงหน้า (เรียกว่า community report) ได้ออกมาเป็นกราฟความรู้หลายระดับ ตั้งแต่รายละเอียดยิบจนถึงภาพรวมกว้าง
2. **Query** — ดึงโครงสร้างนี้มาเป็น context เสริมให้ LLM ตอนตอบ

### สองโหมดการค้นที่ต้องเข้าใจ

| โหมด | เหมาะกับ | ตัวอย่างคำถาม |
|------|---------|--------------|
| **Local search** | คำถามเจาะจง เกี่ยวกับ entity ใด entity หนึ่ง | "บริษัท X มีความสัมพันธ์กับใครบ้าง" |
| **Global search** | คำถามภาพรวมทั้ง corpus | "ธีมหลักของข้อมูลทั้งหมดคืออะไร" |

โดย global search ทำงานแบบ map-reduce คือแตก community report เป็นชิ้นๆ ให้ LLM สรุปทีละชิ้นพร้อมให้คะแนนความสำคัญ แล้วรวมเฉพาะจุดที่สำคัญที่สุดมาตอบรอบสุดท้าย ส่วน vector RAG เดิมของคุณยังเหมาะกับคำถามแบบ who/what/when/where ที่คำตอบอยู่ในข้อความเฉพาะจุด

### พัฒนาการล่าสุดที่ควรรู้ (และเอาไปพูดตอนสัมภาษณ์ได้)

- **DRIFT search** — รวม global + local เข้าด้วยกัน เป็นโหมดที่แนะนำสำหรับคำถามที่ต้องทั้งกว้างและลึก
- **LazyGraphRAG** — ตัวแก้ปัญหาเรื่อง "แพง" ของ GraphRAG โดยเลื่อนการสกัดกราฟออกไป ทำให้ต้นทุน indexing ลดลงมหาศาล (เคลมว่าลดได้ระดับ ~0.1% ของ GraphRAG เต็ม) เป็นทางเลือกที่ practical กว่ามากสำหรับโปรเจกต์ส่วนตัว

### ⚠️ คำเตือนสำคัญเรื่องต้นทุน

GraphRAG เต็มรูปแบบ **แพง** ขั้น indexing เผา token จากการให้ LLM อ่านและสกัดทั้ง corpus มีรายงานว่า corpus ขนาด 1MB อาจมีค่า API ราว $5–20 ขึ้นกับโมเดล ดังนั้น:

- **เริ่มจาก corpus เล็กๆ** เสมอ อย่าเพิ่ง index ของใหญ่
- พิจารณาใช้ **LazyGraphRAG** หรือไลบรารีเบาๆ (เช่น nano-graphrag) แทนตัวเต็ม
- หรือใช้ **local LLM ของคุณเองในขั้น indexing** เพื่อตัดค่า API ออก — ซึ่งเข้าธีม hybrid ของโปรเจกต์นี้พอดี และเป็นจุดขายที่ดี

### วิธีต่อยอดเข้ากับโปรเจกต์เดิม

ข้อดีคือไม่ต้องรื้อของเดิม ให้ทำเป็น **retrieval อีกเส้นหนึ่ง** ขนานกับ hybrid retrieval ที่มีอยู่:

1. เพิ่ม pipeline สร้างกราฟ + community summary (ใช้ local LLM สกัดเพื่อคุมต้นทุน)
2. ใส่ logic ให้ router เลือก: คำถามภาพรวม → GraphRAG global, คำถามเจาะจง → hybrid retrieval เดิม
3. **เอา eval harness จาก Phase 3 มาวัดเทียบ** ว่า GraphRAG ดีกว่า hybrid RAG บนคำถาม "ภาพรวม" จริงไหม และแพงกว่าแค่ไหน

ข้อ 3 นี่แหละคือทอง — คุณจะมีตารางที่โชว์ว่า "บนคำถามประเภทไหน เทคนิคไหนชนะ และคุ้มต้นทุนไหม" ซึ่งเป็นการตัดสินใจเชิงวิศวกรรมที่คนจ้างงานระดับ senior มองหา

## กับดักที่พบบ่อย (ระวังไว้)

- **chunking ห่วยทำพังทั้งระบบ** — retrieval ดีแค่ไหนก็ช่วยไม่ได้ถ้า chunk แบ่งมั่ว ลงทุนกับขั้นนี้
- **ข้าม evaluation** — แล้วจะไม่มีทางรู้ว่าที่ปรับไปดีขึ้นจริงไหม อย่าข้าม Phase 3 เด็ดขาด
- **context ยัดเยอะเกินไป** — ใส่ chunk เยอะไม่ได้แปลว่าดีขึ้น บางทีแย่ลงเพราะ noise
- **ลืมเคส "ไม่มีคำตอบ"** — ระบบที่ดีต้องกล้าตอบว่าไม่รู้ ไม่ใช่มั่วทุกครั้ง
- **เริ่มที่ vLLM เลย** — ตั้งค่ายุ่งกว่า เริ่ม Ollama ให้ทะลุก่อนแล้วค่อยย้าย

## ลำดับลงมือ (ถ้าจะเริ่มวันนี้)

1. เลือก dataset ที่เฉพาะทางพอจะโชว์คุณค่า RAG
2. ตั้ง Ollama + pgvector ด้วย docker-compose
3. ทำ Phase 1 ให้ทะลุปลายทางก่อน — อย่าเพิ่งสนใจคุณภาพ
4. พอ MVP เดินได้ ค่อยไล่ Phase 2 → 5 ทีละขั้น โดยมี eval เป็นเข็มทิศ

เริ่มเล็ก ทำให้เดินได้ก่อน แล้วค่อยทำให้ดี — และวัดผลทุกขั้น
